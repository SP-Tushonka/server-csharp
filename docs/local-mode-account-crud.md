# Local-mode account CRUD correction

This branch derives from frozen mode source 196fab5bbbbde8ef73ca3fa2d12b404bce0ca304. It corrects a reproduced compatibility regression without changing the accepted Core or any real account.

The 15-check baseline fixture used actual LauncherV2Controller and services on disposable accounts. Registration/login/list filtering and wipe marking worked, but an internal child could authenticate and be removed by username. Root removal retained its child/index entry; a new LocalGameModeService then rejected an unrelated surviving account with `Unknown account in local mode index`.

The five changed Core files keep canonical controllers as the entry points. Launcher login/remove/wipe resolve ordinary accounts only. Wipe reuses the filtered resolved ID, even when a legitimate account and internal child share a username. Memory-only DeleteProfileById remains unchanged because normal character recreation uses it before replacing character data. Account list filtering hides partial internal ownership metadata too.

Physical RemoveProfile serializes with mode provisioning before checking whether index.json exists. Its ordered existing save-lock set includes index IDs even when normal recreation temporarily unloads a child, plus loaded owner claims. A validated durable deletion intent covers only the root and its two indexed children. Index/profile ownership, IDs, duplicate references and raw hashes are checked before mutation. The flushed intent is the explicit-delete commit point. On a filesystem failure, committed targets are removed from memory so a later background save cannot recreate them; startup completes the exact intended deletion. No profile bodies or wallet data enter the journal.

Recovery is idempotent when some files are already absent. Changed target bytes, changed index text, malformed journals and unowned/aliased index entries refuse without overwriting new data. Leading UTF-8 BOM is skipped only for JSON ownership parsing; the entire original byte sequence remains hashed. An unindexed owned child, including an interrupted first provision, refuses root deletion for later explicit recovery. It is never swept by name or automatically deleted. The ordinary already-absent root-file path remains available only with no index and no claimed owned children.

The CRUD fixture covers real filesystem deletion denial after the root was removed, startup SaveServer.LoadAsync recovery, remaining account usability, pending save locks, stale-save refusal, child-recreation lock coverage, first provisioning with missing index, concurrent index publication/deletion, malformed/duplicate/unowned index refusal, orphan refusal and canonical BOM loading/deletion. The compatibility fixture reuses the existing mode/store/BattlePass/WS/raid checks unchanged. Wipe coverage is actual LauncherV2Controller.Wipe marking/edition and TarcoinStoreService.CarryOverPurchases; full template recreation end to end is not claimed. Arbitrary concurrent character recreation safety beyond the tested indexed save-lock seam is not established.

Create the separate source checkout with GIT_LFS_SKIP_SMUDGE=1; no game database LFS payload is needed for these synthetic fixtures. Reproduction requires the existing .NET10 SDK and offline NuGet cache. With NUGET_PACKAGES set to <your NuGet package cache>, build Libraries/SPTushonka.Server.Core/SPTushonka.Server.Core.csproj in Debug using --configfile Testing/LocalModeCrudFixtures/NuGet.Config -p:NuGetAudit=false -p:BuildInParallel=false -m:1. Then run Testing/LocalModeCrudFixtures/ModeCrud.csproj and Testing/LocalModeCompatibilityFixtures/ModeRegression.csproj in Release with RestoreConfigFile set to that same offline config. Pass CoreDirectory for the newly built Core output, and DependencyDirectory for the published matching Common/DI and Spectre dependencies. Defaults use the Core Debug output. No machine-specific dependency directory is embedded. They create and delete only generated temporary synthetic user directories, and start no HTTP server or game.

No migration, actual profile deletion, deployment or accepted-package change is authorized by a passing fixture. Runtime owns review and later guarded integration. Exact source/artifact pins and observed results are recorded separately after the committed-source rebuild.
